## 📋 개요

여행 중 매장별 쇼핑 리스트를 관리하는 **개인용 모바일 웹앱**.

- **대상:** 본인 1인
- **시나리오:** 여행 전 매장별 물건 등록 → 현장에서 핸드폰으로 확인 → 구매 시 체크
- **핵심 제약:** 해외 이심(느린 인터넷) 환경에서도 빠르게 동작해야 함

## 💬 논의 & 결정 사항

### Q1. 프레임워크 선택: Next.js vs React vs 순수 HTML?

**배경:** 사용자가 속도를 최우선으로 요구. 해외 이심 환경에서 인터넷이 느릴 수 있음. 어떤 프레임워크가 가장 적합한지 결정 필요.

**대안 검토:**

- ✅ **Next.js 15 + PWA** — SSG로 초기 HTML 미리 생성하여 빠른 첫 로딩. Service Worker로 오프라인 캐싱. Supabase와 연동 간편. Vercel 무료 배포. 이미지 최적화 내장.
- ❌ **순수 HTML/JS** — 가장 가볍지만, 사진 업로드/DB 연동/라우팅을 직접 구현해야 함. 개발 속도 느림. PWA 설정도 수동.
- ❌ **React (Vite SPA)** — CSR이라 첫 로딩 시 빈 화면 + JS 파싱 필요. SEO 불필요하지만, 초기 로딩 속도에서 SSG 대비 불리. PWA 설정은 가능하나 Next.js 대비 이점 없음.

**결정:** Next.js 15 (App Router) + PWA 조합. SSG로 빠른 초기 로딩 + Service Worker로 오프라인 지원. 느린 네트워크에서도 캐싱된 페이지 즉시 표시.

**계획 반영:** 기술 스택 섹션, Phase 3 PWA 설정, 속도 최적화 전략에 반영.

### Q2. DB로 Supabase가 맞는지?

**배경:** 사용자가 Supabase를 고려 중. 간단한 개인 프로젝트에 맞는 DB 필요. 사진 저장도 필요.

**대안 검토:**

- ✅ **Supabase** — PostgreSQL + Storage 올인원. 무료 플랜(500MB DB, 1GB Storage) 충분. 이미지 업로드 Storage 내장. 관계형 데이터(장소→매장→아이템)에 적합.
- ❌ **Firebase** — NoSQL이라 계층 관계 표현 불편. 실시간 기능은 과잉.
- ❌ **localStorage만** — 사진 저장 용량 한계, 기기 바꾸면 데이터 날아감.
- ❌ **JSON + GitHub Pages** — 동적 수정 불가.

**결정:** Supabase 채택. 관계형 DB + 이미지 Storage + 무료 플랜 = 이 프로젝트에 최적.

**계획 반영:** 기술 스택 섹션, Phase 1 전체에 반영.

### Q3. 느린 인터넷 대응 전략

**배경:** 해외 이심 사용 시 인터넷이 불안정할 수 있음. 매장에서 리스트를 확인하려는데 로딩이 안 되면 무용지물.

**대안 검토:**

- ✅ **PWA + 공격적 캐싱** — 한 번 로드하면 오프라인에서도 리스트/사진 확인 가능. 체크 토글은 온라인 복귀 시 동기화.
- ✅ **이미지 최적화** — 썸네일(200px) 우선 로드, 원본은 탭 시 로드. WebP 포맷으로 용량 50% 감소.
- ✅ **낙관적 업데이트** — 네트워크 응답 기다리지 않고 즉시 UI 반영. 실패 시 롤백.

**결정:** 3가지 전략 모두 적용. PWA가 핵심 — 여행 전 Wi-Fi에서 앱 한 번 열어두면 이후 캐싱으로 빠르게 동작.

**계획 반영:** Phase 2 속도 최적화 전략, Phase 3 PWA 설정, 구현 순서 Step 6에 반영.

**제안 목록:**

### Q5. Notion으로 대체 가능한가?

**배경:** 사용자가 "그냥 노션으로 보는게 나을까? 해외 데이터 환경에서 잘 보일라나" 질문.

**대안 검토:**

- ❌ **Notion** — 초기 로딩 무거움(JS 수 MB). 3G 환경에서 10초+ 소요 가능. 오프라인 지원 약함. 캐시 안 된 페이지는 인터넷 없으면 열리지 않음. 이미지 많으면 스크롤마다 로딩 대기.
- ✅ **커스텀 PWA** — 한 번 로드 후 오프라인 완전 동작. 이미지도 캐싱. 매장에서 즉시 확인 가능. 체크 토글 즉각 반응.

**결정:** 커스텀 PWA 유지. 매장 안에서 실시간으로 리스트 확인하는 게 주 시나리오이므로, Notion의 느린 로딩은 치명적. PWA는 여행 전 Wi-Fi에서 한 번 열어두면 이후 완전 오프라인 동작.

**계획 반영:** 오프라인 지원을 핵심 기능(F4)으로 격상. 기술적 근거 강화.

### Q6. Supabase 연결과 SQL 실행은 어떻게?

**배경:** 코드는 구현되어 있지만, 실제로 Supabase 프로젝트에 연결하고 테이블을 생성해야 앱이 동작함. "supabase에 연결해야되지않아? 그리고 sql문으로 만들어야하고."

**필요한 작업:**

1. **Supabase 프로젝트 생성** — [supabase.com](https://supabase.com)에서 새 프로젝트 생성
2. **환경변수 설정** — 프로젝트 Settings > API에서 URL과 anon key를 복사하여 `.env.local` 작성:
   ```
   NEXT_PUBLIC_SUPABASE_URL=https://xxxxx.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIs...
   ```
3. **SQL 마이그레이션 실행** — Supabase Dashboard > SQL Editor에서 `supabase/migration.sql` 내용을 붙여넣고 실행. 이것으로 테이블(places, stores, items) + 인덱스 + RLS 정책 + Storage 버킷이 한번에 생성됨.

**결정:** `.env.local.example` 파일에 설정 예시를 이미 제공함. `supabase/migration.sql`에 전체 스키마가 한 파일로 정리되어 있어 SQL Editor에 복붙하면 끝.

**계획 반영:** 구현 결과 > 주의 사항 + 다음 단계에 반영 완료.

### Q7. 단일 매장(돈키호테)은 장소→매장 2단계가 불편하다

**배경:** 캐널시티 같은 복합몰은 장소(캐널시티) → 매장(마크샵 2F, 돈키호테 3F) 구조가 자연스럽다. 하지만 독립 매장(돈키호테 단독점 등)은 장소 추가 → 또 매장 추가 → 그제서야 아이템 추가라서, 같은 이름을 두 번 입력하는 불편함이 있다.

**대안 검토:**

- ✅ **스마트 내비게이션 (자동 건너뛰기)** — 장소에 매장이 1개뿐이면, 장소 카드 탭 시 매장 목록을 건너뛰고 바로 아이템 목록으로 이동. 복합몰(매장 2개 이상)은 기존처럼 매장 목록 표시. 장소 추가 시 "단일 매장" 옵션을 두어 같은 이름의 매장을 자동 생성.
- ❌ **계층 제거 (2단계 → 1단계)** — 장소 개념 없이 매장만 나열. 캐널시티처럼 같은 건물 내 여러 매장을 묶어보는 기능을 잃게 됨.
- ❌ **아이템을 장소에 직접 추가** — DB 스키마 변경 필요(items.store_id가 nullable로), 코드 복잡도 증가. 현재 구조와 충돌.

**결정:** 스마트 내비게이션 채택.

1. **장소 추가 시**: "이 장소에 매장이 여러 개인가요?" 토글 추가. OFF(기본)면 같은 이름의 매장 자동 생성 → 바로 아이템 추가 가능.
2. **장소 탭 동작**: 매장 1개면 → 아이템 목록 직행. 매장 2개 이상이면 → 매장 목록 표시.
3. **기존 데이터 구조 유지**: DB 변경 없음. 단지 UX 흐름만 개선.

**계획 반영:** Phase 2 Frontend > 페이지 구조 및 구현 순서 Step 4에 반영 필요. 구현 시 홈 페이지 장소 카드 클릭 동작 + 장소 추가 모달 수정.

**구현 완료 (v1.4):**
- `src/app/page.tsx`: 장소 추가 모달에 "복합몰" 토글 추가. OFF면 동일 이름 매장 자동 생성.
- `src/app/page.tsx`: 장소 카드 클릭 시 `single_store_id`가 있으면 `/store/[id]`로 직행.
- `src/app/api/places/route.ts`: 응답에 `single_store_id` 필드 추가 (매장 1개면 해당 store id 반환).
- `src/lib/types.ts`: `PlaceWithStats`에 `single_store_id` 필드 추가.

### Q8. 매장별 혜택/할인 정보를 한눈에 보고 싶다

**배경:** 돈키호테 네이버페이 포인트 결제 시 만엔 이상 10% 할인처럼, 각 매장마다 적용 가능한 혜택/할인 정보가 있음. 현장에서 결제 전에 이걸 빠르게 확인하고 싶다.

**대안 검토:**

- ✅ **매장(Store) 모델에 `benefits` 필드 추가** — stores 테이블에 `benefits text[]` (텍스트 배열) 컬럼 추가. 매장 추가/수정 시 혜택을 여러 줄 입력 가능. 매장 카드와 매장 상세 상단에 혜택 뱃지/리스트로 표시.
- ❌ **별도 테이블** — 혜택 정보만으로 별도 테이블을 만들면 과잉 설계. 매장당 혜택 수가 적으므로 배열 컬럼이면 충분.
- ❌ **memo 필드 활용** — 이미 memo가 있지만, 혜택은 시각적으로 강조해야 의미가 있음. memo에 섞으면 놓치기 쉬움.

**결정:** stores 테이블에 `benefits text[]` 컬럼 추가. 매장 카드에서 혜택을 눈에 띄게 표시 (태그/뱃지 형태). 매장 추가/수정 모달에 혜택 입력 UI 추가.

**계획 반영:**
- Phase 1: stores 테이블에 `benefits` 컬럼 추가
- Phase 2: 매장 카드 UI + 매장 추가/수정 모달에 혜택 입력

### Q9. 친구들과 함께 쓸 수 있게 (멀티유저)

**배경:** 같이 여행 가는 사람들이 각자 자기 쇼핑 리스트를 만들어서 사용하고 싶음. 기본적으로 내 목록만 보이고, "둘러보기"로 친구들이 뭘 담았는지 구경 + 나도 담기 가능.

**대안 검토:**

- ✅ **간단 이름 로그인 + 유저별 목록** — 비밀번호 없이 이름만 입력해서 진입. 유저별로 아이템 체크 상태 분리. 장소/매장은 공유, 아이템 목록(체크 상태)은 개인별.
- ❌ **Supabase Auth (이메일/소셜 로그인)** — 간단한 여행용 앱에 회원가입은 과잉. 친구한테 "구글로 로그인해" 하면 귀찮음.
- ❌ **공유 링크** — URL 공유는 간편하지만 개인별 체크 상태 분리가 어려움.

**설계:**

1. **유저 모델:** `users` 테이블 — `id`, `name`, `created_at`. 이름만 입력하면 생성.
2. **세션 관리:** localStorage에 user_id 저장. 이름 입력 화면은 첫 진입 시만.
3. **데이터 분리:**
   - 장소(places) / 매장(stores) → **공유** (모든 유저가 동일하게 봄)
   - 아이템(items) → **유저별** (`user_id` 컬럼 추가). 각자 자기 아이템만 기본 표시.
4. **둘러보기:** 친구 목록을 읽기 전용으로 탐색. "나도 담기" 버튼으로 내 목록에 복사.
5. **RLS 업데이트:** items는 자기 user_id만 CRUD, 다른 유저 items는 SELECT만 가능.

**결정:** 간단 이름 로그인 + 유저별 아이템 분리 채택. 장소/매장은 공유.

**계획 반영:**
- Phase 1: users 테이블 추가, items에 user_id 컬럼 추가, RLS 수정
- Phase 2: 이름 입력 화면, 둘러보기 페이지, "나도 담기" 기능
- 구현 순서에 Step 8 추가
